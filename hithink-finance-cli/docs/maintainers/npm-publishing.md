# npm Publishing

Releases use the public repository's `hithink-finance-cli-release.yml` workflow and npm Trusted Publishing. Run local CLI commands from `hithink-finance-cli/`.

1. Confirm `package.json`, `npm-shrinkwrap.json`, the generated Skill manifest and CHANGELOG use the intended version. Keep the approved `LICENSE` in the package. The package's `repository.url` must match the public GitHub repository for provenance verification, including capitalization.
2. Validate affected inputs and record their SHA, platform and result. Automatic CI runs the Linux/Node 24 baseline once; use the CLI CI workflow's manual `platform` input (`all`, `windows`, `linux`, `macos`) for platform coverage. Authentication, permissions, process and native-dependency changes need corresponding platform validation. Generate contracts when they change; run Python SDK checks when Python is affected. Reuse unchanged-input evidence.
3. Confirm the target repository and maintainer permissions, check that the intended npm version is unused, and verify the workflow's npm Trusted Publisher configuration.
4. After building, run `npm run verify:release-package -- <new-empty-output-directory>`. It packs once with scripts disabled and installs that tarball into an isolated prefix. The install prefers cached dependencies and fetches missing package data from the configured registry. Prime dependencies with `npm ci --ignore-scripts` when needed. The check uses an isolated home and verifies version, capabilities, fresh auth status, doctor/native DuckDB and bundled Skill hashes. It retains the verified tarball for publication. Changes to login or Skill delivery require separate acceptance.
5. After publication authorization, push the public candidate and wait for the successful main push at that exact SHA. It builds, checks the license, installs and verifies the tarball, then uploads that file with its integrity and run identity. Complete applicable platform acceptance before creating the `v<version>` tag. The tag workflow verifies the downloaded archive against that main push, publishes the same file with provenance, then creates the GitHub Release. Stable versions use `latest` and prereleases use `next`. Keep the candidate version fixed while repairing checks. Confirm publication status in npm and GitHub and obtain specific authorization before replacing an unpublished tag.
6. Read back the published version and dist-tag from the official registry, then verify a fresh installation. Record the exact version, tarball integrity and validation results.

The release job downloads the artifact for the selected main push run and attempt. It checks the repository, source SHA, package name, version and SHA-512 before running `npm publish <verified-tarball> --ignore-scripts --provenance`. The artifact retention request is 14 days. If the artifact is missing or expired, re-run all jobs of the existing main push for that SHA, then retry the workflow on the same tag. GitHub permits reruns for up to 30 days after the initial run. For an already-published version, recovery on the tag can create its missing Release directly. [GitHub Actions reruns](https://docs.github.com/en/actions/how-tos/manage-workflow-runs/re-run-workflows-and-jobs)

Local manual publishing retains `prepublishOnly`. CI/test/documentation-only changes do not require another CLI version. Preserve the required checks and the published tags' original workflow definitions.

For WorkBuddy, generate the connector with `node scripts/package-workbuddy.mjs <new-output-directory> <approved-auth-domain> [connector-version]` after building. The optional connector version defaults to the CLI version; the minimum CLI version always comes from package.json. The required CLI version must already be published before submitting the connector. The generated auth command uses foreground completion with `authWaitForExit: true`; WorkBuddy opens the printed URL and waits for the result. Test installation, browser authorization, cancellation, status, logout, restart and expired credentials in the real host on supported platforms.

The connector icon is `assets/workbuddy/icon.png`, copied unchanged from the frontend project's `apps/docs/static/img/favicon.png`. Refresh this asset from the official frontend icon when branding changes.
